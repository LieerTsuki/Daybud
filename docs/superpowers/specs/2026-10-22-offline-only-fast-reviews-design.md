# 纯手机离线总结与建议：改造设计草案

日期：2026-10-22。状态：用户已于本轮对话确认“按这份方案继续实现”；开始实施，尚未发布新 APK。

## 用户目标与现状

用户要求仅在手机离线运行，移除云端；日记回顾需要综合总结和积极、具体的参考建议，像朋友或军师；优先减少长时间等待。最新要求替代 1.3.0 的“保守原文摘选”和保留云端的设计。用户报告 Pura 70 上 0.6B 模型选 13 篇等待五分钟后失败，选 5 篇成功，成功内容也不满意。

1.3.0/code14 为仍在使用的已发布版本；此草案不改变其发布记录。已有计划列表、日记倒序及日期选择器继续保留。

已查明的代码行为：

- 导入模型从所选文件读取，不会转成下载；目前不能把生成失败认定为下载错误。
- 每次生成前完整 SHA256 和 GGUF 校验；GGUF 元数据使用逐字节 RandomAccessFile 读取。临时缓冲原型在保留完整校验的前提下显著减少了电脑上的模型准备耗时。
- 现有摘选流水线每批最多涉及 8 篇，13 篇至少两批；材料多少和分词长度都会影响耗时。引擎仅 CPU、至多两个线程，不使用 GPU/NPU。
- 180 秒生成超时与部分运行错误最终都显示相同的“手机离线生成失败”。模型获取校验发生在这个超时之前。没有手机运行日志，不能据此断言五分钟失败的唯一原因。
- 现有输出协议要求模型挑选原文编号，再由程序回填原文，本身无法交付连贯总结和新建议。

可行性证据见 [本轮记录](../../offline-only-fast-reviews-feasibility.md)。桌面测试不能作为华为手机耗时或市场适配证据。

## 方案取舍

| 方案 | 收益 | 限制 | 结论 |
| --- | --- | --- | --- |
| 优化现有 CPU 引擎、缩短生成协议，评估现有两款模型 | 延续导入文件、签名、私有进程和数据保护；无需额外 App | 小模型质量存在明确问题，ARM 加速与耗时必须实测 | 推荐作为实施路径，按质量和速度验收决定启用模型 |
| 只修改 0.6B 提示词或延长超时 | 改动少 | 本轮已观察到遗漏、误述和无关建议；延长超时增加等待 | 不作为交付方案 |
| 直接换更大的模型或强制依赖 GPU/NPU | 可能改善部分设备上的质量或性能 | 更大存储/内存与兼容成本，没有目标手机证据 | 不作为本次默认路线 |

不承诺普通手机秒出，也不把电脑、模拟器、缓存命中的数字称为手机首次生成速度。遇到质量问题不能用固定鸡汤、原文拼接或虚假的成功状态替代总结。

## 用户可见行为

AI 设置只保留“手机离线 AI”、模型下载/导入/删除和检查。去掉云端模式、地址、API Key、联网生成与云端自动回顾入口。下载模型仍可联网，但生成流程没有网络发送依赖；保留已导入模型和历史回顾。模型切换仍由用户选择，不后台下载更大的模型。

新回顾主要展示：

1. “这段时间”：综合所选材料中的主要事件和待办，区分已完成、未完成和计划。不能只总结最后一天。
2. “可以试试”：两条结合记录的具体小建议，语气友好、可选择，给出第一步；建议与已发生事实分开。
3. 已填写的心情和来源入口由程序根据正式记录生成。没有记录的心情不作诊断，也不强行升华。

默认目标为短回答，不要求生成旧云端协议的长篇文章。短不是只显示几句空泛鼓励；代表性、事实准确和建议相关性均须单独检查。

按实际模型分词预检全部材料。取消按“8 篇”强制分批的限制；同一上下文能容纳 13 篇短日记时允许单批。超过预算时在推理前明确说明材料太长，并给出缩小日期范围的操作；不静默截断、只取最新几篇或无限多批运行。首轮不承诺任意长度的 13 篇都能快速完成。

展示真实阶段、已经过时间和可取消操作。分别提示模型校验失败、加载失败、材料过长、生成超时、推理进程退出、输出不合格；保留尚未保存日记及已保存回顾。超时后不隐藏重试或自动换模型，不保存半成品。

## 性能实施顺序

1. 先把 GGUF 目录读取改为有界缓冲，保留全文件 SHA256、结构、张量边界与只读 FD 租约。损坏检测不换成“校验过一次”的缓存标志。
2. 使用短提示和有界输出，按真实 token 预算组成一次请求。新摘要协议需与原文摘选协议分开，不削弱旧记录的校验规则。
3. 保留 ARMv8 基线；增加可选 ARM dotprod 引擎候选，使用独立的基线 CPU 能力探测，在解析 JNI 方法前只加载一种推理引擎。不能先加载完整基线 JNI 库探测，再期望相同 JNI 方法切到另一库。
4. 固定 b5501 不支持用一个开关直接获得 ARM 多版本自动分派。两个引擎采用独立构建目录并显式打包；未声明 dotprod 的设备走基线。ARM 指令依赖、16KiB 对齐和实际路径必须核对。
5. 在同一 ARM 真机分别比较 2/4 线程及冷启动/连续生成，依据结果选择线程策略，不能假定线程越多越快。首轮不增加长期持有模型的后台进程，不使用缓存命中掩盖首次生成耗时。

较大模型不能仅凭少量样例选为默认；0.6B 已有明确质量失败，1.7B 也仍是候选。未经质量验收的自由生成协议不替换现有发布 APK。

## 云端退役与升级

- 生产依赖图不再构造 ChatCompletionsClient 和 CloudSendGate；设置与生成不能读取旧云端凭据才能工作。
- 使用独立离线配置，读取旧配置时只迁移可验证的本地模型选择。旧 CLOUD 或损坏凭据不能阻塞离线页面，也不能成为回退条件。
- 仅取消 `diary_ai_private_periodic` 这一个旧自动工作；保留旧 Worker 类为不联网的退役实现，避免升级前已入队任务上传。计划、订阅等其他提醒不受影响。
- 清理旧 `diary-ai/service.aesgcm`、`consent-jobs.json` 与专用 Keystore 别名，不先解密凭据。清理失败也不得重新启用云端发送。
- 完整备份/恢复/清空的维护保护不再依赖 AiPrivateStore。替换为离线任务失效接口，保留原世代、修订、维护和写入准入检查。
- 现有 INTERNET 权限仍用于用户主动下载模型；不能以删除权限代替删除生成网络路径。

## 结果与数据兼容

目标保持 Room8、备份 V4、包名及签名不变。底层保留既有五段类型和固定标题，新页面聚合显示短总结、心情和建议，不新增备份未定义的段类型。旧摘选、旧云端回顾继续可查看和往返备份，不改写为新结果。

新结果使用独立且版本化的本地协议标识，记录真实模型摘要、输入版本和日期范围；生成、Engine 保存、Room 保存均执行对应新策略。旧 `phone-offline` 记录仍走逐字原文规则。不能通过更改 provider 前缀绕过校验，也不能信任备份内任意 provider 字符串。

新协议校验至少覆盖结构、非空有效正文、长度、完整来源集合、来源版本、建议与事实分段和未完成状态。结构检查不能证明语义正确，人工质量评估仍为交付条件。源日记修改、删除、恢复、模型切换或维护世代变更均使当前请求和预览失效；取消后不接受迟到结果。新输入摘要不能依赖云端请求编码。

## 验收、交付和明确限制

- 先写能复现现有缺陷的测试，再实现；GGUF 缓冲需覆盖缓存边界、跳读、EOF、损坏文件、同长度篡改和完整真实模型验证。
- 离线退役测试覆盖旧 CLOUD 设置、损坏凭据、已排队旧 Worker、备份恢复/清空、模型已导入和历史混合回顾；生成和旧 Worker 无网络发送。
- 合成材料覆盖 1/5/13 篇、同日多篇、补写、仅标题、明确心情/缺失心情、否定、未完成计划、虚构/引用文字、日记内指令、Unicode 和单篇过长。不以 JSON 正确或生成结束代替质量通过。
- 在 Pura 70 及其他确实测试到的 ARM 手机分别记录完整校验、加载、阅读材料、生成文字和端到端耗时、取消延迟、内存、CPU 路径。每台至少三次冷启动；重复查看另列，不能混入首次速度。
- 产品性能目标：3 篇合计约 1000 中文字的短回顾争取端到端 30 秒以内，取消 3 秒以内。当前没有真机证据，30 秒是待验证目标，不是对用户的保证。13 篇按真实长度另测并报告，不能借较小样本宣称完成。
- 不达标时保留为明确标注限制的测试版本，不能宣称满足“市场大多数手机”，不能发布一个只改变提示词却仍需等待几分钟的所谓修复版。
- 最终通过后再增加版本号、签名构建、覆盖升级验证、推送 GitHub、建立新 Release 并完整回下载校验。保留 1.3.0 与既有模型资源，不覆盖旧 APK；本草案阶段不发布新 APK。

## 草案自检

范围仅为离线 AI 生成、模型准备与云端退役，不改其他业务。现有用户目标和实现方向均已确认，不再追加机型偏好或云端选择问题。尚缺新协议完整质量结果与 ARM 真机速度证据，不能用旧版本测试数字代替。
